Your world, proven.

Skein is one graph for everything you do: your files and code, your coins and contracts, the proofs behind them, and every message in or out. Everything is signed as it happens. Anchor any of it to Bitcoin whenever you want anyone to be able to check it.

Git did this for source code: every copy carries its whole history, and anyone can verify it. Skein does the same for your part of Bitcoin, and for the work around it.

Why

Work is scattered

One project lives in several repos on several machines. The coding assistants from different providers each keep their own history and memory. Your coins sit in a wallet, their proofs with an indexer, your tokens with another service. Nothing connects them, and most of it can't be checked after the fact.

Skein started as a way to put all of that in one graph you can traverse: an index and a change history for a whole working life, whether a person or a program did the work.

Git, Bitcoin, signed messaging and language models grew up as separate worlds. Skein is where they meet, and each supplies something the others lack.

How it builds up

Built up in layers

Start with the graph. Everything after it is something running on the graph, and it all goes into the same record.

1 · the graph

Your world, proven

Useful with nothing running in it.

Files and directories, coins and transactions, block headers and proofs are all records in a single content-addressed store. Signed messages are the only way anything gets in or out, so the record is complete: if it happened, it's in the graph, with the signature of whoever sent it.

Every change is signed as it happens. Anchoring is separate, and it's your choice: put a checkpoint, a single file or the whole graph on chain, as often as it's worth paying for.

Technical details

records
Content-addressed blocks: CIDs over dag-cbor, sha2-256. Files are git blobs and trees, so a git repository is already a subtree of the graph. built
index
Merkle search trees behind one state record, so the whole state has a single hash that you can sign, anchor or compare. built
messages
BRC-33 message box and BRC-169 envelopes over BRC-103/104 mutual auth. The sender signs the content hash. Messages are encrypted on the wire, and the log holds the plaintext. built
wallet
BRC-100. Keys never enter the VM: it asks a signing oracle. UTXOs, headers, Merkle proofs and transaction status are records in the graph like everything else. in progress
anchoring
A checkpoint is a BEEF packet whose scope is a state record. gib puts git on chain: write-once outputs, ordfs/dir directories, branch pointers as commit tokens. in progress
2 · programs

Things that act on it

A robot, programmed or not.

A program runs inside the skein and works only on the graph. It reads files, writes trees, asks the wallet to sign and sends messages. It might be a scheduled job, a fixed workflow or a model deciding what to do next. To the graph they look the same, and every step each one takes is recorded.

Because the record is complete, any step can be replayed and gives the same result. You can check what happened by running it again, not just by reading a log someone wrote about it.

Technical details
the VM
A WASI machine: preview 1 modules and WASI 0.2 components, on a Zig kernel over wasmtime. Programs target WASI, not skein. built
no side doors
No disk, network, clock or process table. Anything that leaves the VM is a message out and a signed message back, recorded and replayed. built
userland
A POSIX-style shell (brush, coreutils, grep, sed, awk, jq, git) plus JavaScript and Python runtimes, all compiled to WASI and running over the graph's files. built
time & chance
"Now" is the arrival stamp on the current entry plus the fuel burnt so far, at 1 ns per unit. Randomness is a stream keyed by the entry's CID. That's why replay is exact. built
fuel
Every step is metered in wasm fuel, and the count is written on the step. This is what billing is based on. built
3 · conversation

Something you can talk to

Most people would call this an agent.

Connect chat to the message box and a program becomes something you work with. It has its own handle, identity and wallet. Each exchange is a signed message in its graph, and its tool calls and results are steps you can read back and replay.

Use any model, or none. Inference is just another party it exchanges messages with.

Technical details
inference
A peer. The prompt goes out as a message and the completion comes back signed by the provider. The model and the reasoning level are chosen per request. built
context
The conversation is part of the graph, so it goes to the model as deltas keyed by node, not as a whole transcript each time. built
tools
The shell, the files, and messages to other identities. A message it sends and the reply it gets are both records. built
4 · many, talking

Where the record matters most

Robots talking to robots, in the open.

Skeins message each other the same way you message them. A funded skein can pay another for work, or pay to stand up a new one. That's powerful, and it should make you a little uneasy.

The answer isn't to forbid it. It's the record: every message between them is signed, every step is recorded, and any of it can be replayed. People need to be able to see what happens between robots, and here they can.

Technical details
one wire
Skein to skein uses the same BRC-169 envelopes as person to skein. There's no separate channel for machines. built
payments
Tolls and quotes ride on the messages, and each program sets its own spending policy. designed
standing one up
A skein asks a host for a new one exactly the way a person does: quote, payment, genesis. designed
Because it's history

Replay, fork, merge

The state is data with a complete history, so you can work with it the way you work with a git repository.

replay

Check any step

Run it again from the log and get the same bytes. Nobody has to take the output on trust.

fork

Branch from any point

Start a new skein from a checkpoint and try something else. The original keeps going.

merge

Bring it back

File trees are git trees, so divergent work merges the way code does.

Where it runs

Anywhere the graph can be read

A skein boots from a system tree: its programs, its configuration and its own files. The tree can come from a directory, a git repository, or a BEEF packet of an on-chain repository, verified offline without trusting whoever hosts it.

When the code comes from the chain, who published it and which version ran are both part of the record, so you get code signing without doing anything extra.

The only interface is the message box. A skein with the same identity can run on a server, on your desktop or in a browser tab, and the parties it talks to can't tell the difference.

Technical details
system tree
bin/*.wasm handlers, etc/config.json, etc/subscriptions.json, plus the skein's own files. The genesis record names the tree. built
chain packet
A BEEF bag plus a scope, verified offline. A packet whose scope is a state record restores a checkpoint. in progress
hosts
A native kernel today. A browser build (the kernel compiled to wasm, IndexedDB as the store) is in progress. in progress
What it costs

Your skein pays its own way

Shared indexers and gateways have answered these questions for free, to get the ecosystem started. A skein does that work for you alone, so it has real costs, and it pays them from its own wallet.

What you anchor, and how often.

When the funds run out, the skein stops. Fund it again and it picks up where it left off. Closing a skein settles every balance before anything is paid out.

Technical details

The host bills the skein's wallet through a one-way payment channel designed

lock
Funds sit in an output that needs both the skein's and the host's signatures, with a timelocked refund to the skein, so they can't be held hostage.
meter
As usage accrues, the skein signs a new version of the spend that pays the host a larger share. The host keeps only the latest one.
settle
The host broadcasts the latest version on a sweep, a top-up or a close. Whatever is left returns to the skein.
Getting one

Four messages to a skein

Standing one up is just a conversation with a host.

  1. you → hostAsk for a new skein under the handle you want.
  2. host → youThe host replies with the minimum funding and a payment address in the new skein's wallet.
  3. you → hostAccept and pay.
  4. hostThe skein starts from its system tree with your key as its admin. A small token lands in your wallet so you can find it again.
