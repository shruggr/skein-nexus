Technical

Architecture

A deterministic WASI machine over a content-addressed graph. It has three layers: one kernel (the machine, its four tables and the signer), the apps that run on it, and the hosts that drive it from outside.

The host judges nothing and routes nothing. The kernel’s dispatch table routes, and everything that matters is decided by programs inside the kernel and written to the store.

Kernel

The machine: store, log, scheduler, the WASI implementation and skein’s own imports, over wasmtime (C API, statically linked). It keeps four tables: objects (blocks by hash), heads (each with an owner), the dispatch table, and the address book. The owner’s admin messages change them, and the kernel does that itself; no program can. One implementation, kernel-zig, which also compiles to wasm32-freestanding for the browser. CLI: skein-kernel serve | replay | shell | dump | fuel.

Apps and the SDK

Everything outside the kernel is an app, installed under its own name: the front door, the messagebox, resolve, the wallet, the chain app, the shell, the chat app, overlays, static sites. An app is a tree of programs with a manifest. It moves only heads under its own name, reads any record whose hash it holds, and a call to another app hands back hashes, not data. A skein installs only the apps it uses. All are written against skein-sdk, a Zig package. The handler programs are Zig, about 100–670 KB each.

Hosts

Whatever drives a kernel from outside: transports, providers, a store and the signer. A host appends what its transports carry in, holds a waiting client until its request’s thread comes to rest, answers the kernel’s signing requests, and carries out what the skein emits through its providers: a web proxy, a broadcaster, a waker, cron, a libp2p node. A provider may be the host’s or anyone’s; the skein knows it only as an address in its book. How a host holds keys, where it stores bytes and how it’s deployed are its own business. There’s a server host and a browser host, and the same history replays under either.

The kernel’s whole surface

admit
The one call in that writes: append a package as it arrived, then run the steps it drives.
answer
Wait until a request’s thread comes to rest, and return its answer. This is how a waiting web client gets its reply.
call
Run a program function over current state. No entry, no writes, not replayed; its fuel goes to the host’s ledger. Only for host-side reads that are not requests, such as the explorer’s pages.
wallet
Out: key operations, answered by the host’s signer. The one call recorded on the step.
emit
Out: committed messages for providers and peers, and broadcast transactions, carried by the host after the step ends.

Data model: git and Bitcoin in one graph

Every durable thing is a record: one IPLD object named by its CID. Git objects, Bitcoin structures and skein’s own records use different codecs and hashes, but they all live in one store and link to each other by CID.

Families of record

Family
Codec · hash · what the CID equals
skein
dag-cbor · sha2-256. Log entries, thread origins and updates, messages, head updates (with their owner), dispatch-table changes, app records, index nodes, the state record.
git
git-raw · sha1. A tree’s CID is its git object id. A scanned directory hashes identically to git write-tree.
bitcoin
bitcoin-block (0xb0) · dbl-sha2-256: CID = block hash. bitcoin-tx (0xb1): CID = txid. Exactly 64 bytes under bitcoin-tx is a Merkle node, whose CID is its Merkle hash.
raw
Wasm modules and the Python stdlib.

Links run from the newer record to the older one by CID, whatever the codec. Only transaction inputs add “spends” edges to the index.

Git mapping

A repository in a tree is an ordinary git repository, except that .git/objects is synthetic: each loose object is served on the fly from its git-raw record, and writes are inflated, sha1-checked and kept as records. No object is stored twice, and there are no packs. A deployed tree is its repository’s tree.

Bitcoin mapping

Headers decode to {version, previousblockhash → link, merkleroot → link, time, bits, nonce}; transactions to {version, vin: [{txid → link, vout, …}], vout, locktime}, with bitcoind’s field names. Proofs are held sparsely: receiving a BUMP (BRC-74) checks its root against the header at that height, then stores each node it reveals. Conflicting nodes and wrong roots are refused. A proofs map records txid → {block, depth, position}, and a proof is rebuilt by walking down from the header by the position’s bits. The chain app keeps this map under chain/, one copy for the whole skein.

Chains

Anything that changes is a chain: an origin (its identity) and updates carrying origin, prev and seq. Point at the origin for “as it is now”, at an update for “exactly this version”. Threads, heads, the dispatch table and the address book are all chains.

The index and the state record

The store is a key→bytes map plus one pointer. Each query the scheduler needs is its own Merkle search tree (fan-out ~32, canonical: the same pairs give the same root in any order): log, unique, chains, updates, threads, resting, sleepers, awaits, edges, heads. One skein-state record holds the log tip and every map’s root. Its CID is the instance’s single mutable pointer and a function of the log: same log, same state CID.

Cost: 2.5–7.5 new index nodes (0.6–4.2 KiB) plus ~1 KiB of state records per log entry. A store may forget what no head reaches, and the log before its last checkpoint.

Edges

The edges map indexes who points at what, derived from records a step keeps: launched-by, depends-on, resolves, record refs, and spends for kept transactions’ inputs. “Who spent txid:vout” is a prefix scan. Rejection propagates along spends, admits and derives-from.

The kernel and VM

A WASI machine where every input is a log entry and every value that didn’t come from the log is recorded. Replay is exact, and computation is metered by instruction count.

ABIs

Programs are WASI preview1 core modules or WASI 0.2 components (world skein:kernel/handler). The kernel tells them apart by the binary preamble and gives both one behaviour: 0.2 filesystem and io calls are answered by the preview1 implementation. Imports the kernel doesn’t answer (sockets, say) link as traps.

Syscalls

Pure
Files, pipes, spawn, stdio, clock, random. Answered inside, deterministically, never recorded.
Recorded
wallet only: the signer. The request and answer are written as a record of the step; replay serves them from there, and a request that differs on replay is a divergence.
Reads
input, get by CID, head, edges. Global: any program reads any record it holds the CID of.
Writes
put, putblock, keep, advance. advance only moves heads under the program’s own app name.
Threads
launch, await (a record, a subject or another thread), deadline, call.
Out
emit: a signed message to a key in the address book, or a broadcast transaction. Sent when the step ends; the answer is a new entry.

Time

The host stamps each entry at admission. Inside a step, t = max(last + 1, stamp + fuel), one unit of fuel per clock tick: time never repeats, never goes back, and is recomputed exactly on replay. A shell and its children share one meter and one clock. Busy-waits end on their own. Sleep and deadlines are a message to the waker, whose answer wakes the thread. A recurring job is a schedule a program sends to the cron provider. There are no wake entries.

Randomness

SHA-256(key ‖ counter) blocks, key = SHA-256(entry CID ‖ thread CID). Python’s random, uuid4, QuickJS Math.random and git’s temp names all draw on it and replay identically. It’s predictable from public records, so secrets are made by the signer instead.

Fuel

wasmtime fuel is on for every step and summed across everything in it (handler, shell, children, nested calls). The limit is fuelPerStep (default 1012); running out ends the step errored, deterministically, and it’s never retried. Kernel calls and the front door’s request steps have their own limit (1010); a kernel call’s fuel is charged to the host ledger. skein-kernel fuel is the billing query. Overhead is 0–9%. In the browser, where V8 has no fuel, the kernel instruments each module to count its own, and the counts match wasmtime’s.

Replay

skein-kernel replay rebuilds a store from its log with no wallet or network. The equivalence suite replays 18 real histories twice, natively, instrumented and in headless Chrome, and requires identical dumps, fuel and explorer pages. Signatures are deterministic (RFC 6979), so they replay too. Crash recovery is replay at hydrate time: a cut-off step runs again.

Userland: the shell app

  • Shell: brush (bash-compatible, Rust) over uutils coreutils, plus find, xargs, diff, jq (jaq), sed, awk, tree and grep. Pipelines run stage by stage, with 64 MiB pipes.
  • git 2.55 in C via wasi-sdk: init to merge (three-way, conflicts), tag, fsck. No remotes, no packs. Commit dates come from the in-step clock, so commit IDs replay.
  • qjs (QuickJS-ng) registered as node with a sync Node shim, and CPython 3.14 with its stdlib mounted read-only. No npm, no pip, no sockets.
  • Size: 13.7 MB for the shell toolset, plus 19.1 MB for the script runtimes.

Browser build

The same kernel for wasm32-freestanding (2.4 MB) in a Worker, with IndexedDB as the store. It needs cross-origin isolation. It runs preview1 modules only, and has no libp2p. Logs cross between browser and native in both directions.

Messages and network

The instance is an HTTP server. BRC-103/104 is the network, BRC-33 is the mailbox, BRC-169 is discovery, and every package that arrives is written as received.

The front door

Each instance has its own origin (<handle>.host, or /@handle). The host appends every request as received, and the kernel runs the front-door program on it as that request’s own thread: the BRC-103/104 handshake and the check of each message happen inside the VM. The host holds the client’s connection until the thread comes to rest. The caller is the identity key the session proved; there are no accounts. Answers are signed on the session through the signer.

Routes are http rows of the dispatch table: a path or prefix, who may call it ("session" for any BRC-104 session, a key, or "*" for an open route like an overlay’s submit), and the program function to call. etc/reads.json gates read routes by caller. A handler answers {status, type?, body, headers?, admit?}; {wait: true} if the answer depends on a thread still running; or {read: true} for a live read. admit lists the messages and events to route.

The persistence rule

Message arrives
Its request, as received, is one entry. The front door’s step routes the mail record it carries; that record keeps the signed BRC-104 request, so authorship verifies from the log with keys alone.
Read or poll
Its request entry, and nothing else moves. Growth is a pruning question.
Handshake
Its request entry. The step writes the session under the head frontdoor/sessions, so sessions survive a restart (they expire after a day).
Acknowledgement
Its request entry; the step admits an :ack event and the reader’s pointer moves.
Sending
Part of the sending step: the signed message it emitted, listed on the update. Not an entry. The answer is an entry.

The dispatch table

A body with replyTo resumes the thread awaiting that record, but only from the identity it was sent to. Otherwise it is routed by the dispatch table: one table of rows (transport, address, sender, program) for message boxes, web paths and libp2p topics alike, first match wins. A row is the permission. The table is a chain that only the kernel writes, on admin messages from the owner or a delegate. No match means it’s recorded and nothing runs.

Mailboxes, delivery, discovery

  • Messagebox program: BRC-33 send/list/ack (JSON or BRC-231 CBOR). An instance’s own boxes keep no list: admission is the acknowledgement, and the log is the queue.
  • Mailbox instances: an outside identity (a person, the inference peer, a browser tab) gets an instance with only the front door and messagebox. There’s no separate messagebox host.
  • Delivery: an emitted message to a mailbox key is delivered by its own thread. The messagebox program acts as a BRC-103/104 client of the recipient’s messagebox, and each HTTP exchange is a message to the web proxy (the fetch provider). Its sessions are kept under the head outbound. The address book (head peers) maps key → transport (mailbox, libp2p, local) and address. Transient failures are retried; an unknown key is “no route”.
  • Discovery (BRC-169) is a program, not core: manifest, then handle → identity key and messagebox, each lookup a message to the web proxy.

One way out: emit and the providers

A step never talks to the network. It emits a signed message to a key in the address book, ends waiting, and the answer is an entry that steps it again. Providers are recipients with keys of their own: fetch (a web proxy), waker, cron and libp2p. Each answers with a signed message. A provider may be the host’s or anyone’s: it is a row in the address book. A broadcast is an unsigned event that the broadcaster queues and retries; the proof comes back as an event, and status reports come from the Arcade the skein broadcast to.

Inference protocol

The chat app’s loop sends {model, thinking?, tools?, parent?, nodes}, where nodes are only the turn records new since the last request, each with its CID and parent. The inference peer stores nodes per sender, walks back to the root and sends the engine the whole chat. If it lacks a node it answers {missing: [cid]} and the loop resends once. The completion arrives as mail with replyTo, and resumes the thread.

libp2p

The host runs a libp2p node (GossipSub with strict signing) for each instance whose dispatch table has libp2p rows, and follows the table live as apps are installed. Each topic message or stream frame is appended as a request and the front door judges it; an accepted message admits what a web submission would. A rejected one is refused and kept in the history; a repeat is ignored. Outbound is a message to the libp2p provider: publish, dial, send, close. The peer key is separate from the identity key and never holds funds.

A transaction submitted over pubsub persists exactly what POST /submit persists, and overlays gossip what they admitted and its proofs (<topic>, -admit, -proof).

Wallet and overlays

The wallet is split in two: the keys stay outside with the host’s signer, and wallet state lives inside as records. One chain app owns the chain state under chain/; the wallet and each overlay keep their own records under their own names and read it.

The signer

The kernel holds no keys. Key operations (get public key, sign, encrypt/decrypt, HMAC, verify) are requests to the host’s signer, which might be a hosting service’s key store, a hardware module, or the user’s own BRC-100 wallet in a browser tab. A signing request carries a key reference and a 32-byte hash, nothing else. How keys are made, stored and derived is the host’s business and outside the skein.

The wallet program

programs/wallet, built on the SDK’s wallet library over bsvz, compiled to wasm. Operations include headers, internalize (BRC-100 internalizeAction on Atomic BEEF), proof, createAction, signAction and list. The builder picks the largest spendable outputs first, sends change to a fresh BRC-29 key, and returns Atomic BEEF with ancestry back to proven transactions. It matches go-sdk’s ProtoWallet byte for byte on shared test vectors. It is an app: a skein that needs no wallet doesn’t install one.

SPV and headers

The anchor is the network’s genesis header, a constant. Every header must link, meet its proof-of-work target and carry the most work. Difficulty adjustment and timestamps aren’t checked, by decision. A payment validates synchronously or fails. A signing-only wallet needs no headers; the full chain (~72 MB) lives only in an instance fed by a header service. Chronicle rules are on by default.

The chain app

One app holds the chain state (headers, transactions, proofs, spends, broadcasts) under chain/, and nothing else writes it. Its interface is ingest a BEEF. What arrives proven (its proofs check against the headers) is recorded and the caller answered at once. What arrives unproven is recorded and broadcast, and the caller is answered on each change: accepted, proven, rejected. Every unproven transaction it holds has a broadcast registered, so the proof is the answer to that broadcast. Headers from a feed and proofs from the broadcaster come in as plain events and validate themselves inside. Status reports come from the Arcade the skein broadcast to, and stay provisional until there’s a proof. The chain app is the only thing that broadcasts, and the host judges nothing.

Settlement

Unproven, proven or rejected is computed, never stored. Rejection bubbles through spends edges; reorgs revert proofs. Settlement is state to read, not an event to push. Threads fork, they don’t replay: a rejection reaches a thread as a new input, and history stays.

Overlays are apps

An overlay is the overlay engine (shruggr/skein-overlay) plus its own topic managers and lookup services, installed under one name, with its wiring derived from config.overlay and shown to the owner at install. It serves BRC-22/24 at its base URL /<handle>/<app> (/submit, /lookup, open). Submit decodes the BEEF once into the step’s write cache, hands it to the chain app, and asks topic managers identify(tx: cid, …). Nothing persists unless a topic admits, apart from the request itself; otherwise it answers 200 with an empty STEAK. A transaction is admitted on the first of an accepted status or a validated proof. Lookup services keep their own maps and get admitted/spent/rejected hooks. Each overlay keeps its state under its own name, so two overlays can run on one skein.

The @bsv/sdk broadcaster and resolver work against an overlay at an origin’s root, but they reject a base URL with a path, so skein does not use them for overlay apps.

Genesis and deployment

An instance’s first log entry, its genesis, names who it is and the tree it boots from. Everything after is a consequence of that entry and the ones that follow.

The system tree

bin/<name>.wasm | .cid | .json   programs
etc/config.json                   defaults, names, feeds, owner, libp2p, scopes
etc/dispatch.json                 rows: box | HTTP path | libp2p topic → program
etc/reads.json                    who may call read routes
SOUL.md, IDENTITY.md, skills/…    the instance's own files

Booting pre-fills the store and writes a genesis naming the tree; processing it sets head main and seeds the dispatch table: the owner’s four admin rows first, then the tree’s. The genesis also fixes the owner, the default limits, the owner’s mailbox and the providers in the address book. A genesis can be bare: the owner’s admin rows and nothing else, with every app installed on top.

Two sources, one loader

  • A directory, scanned into git objects, or a tree CID already in a store.
  • A chain packet: a BEEF bag plus a scope CID, verified offline for scope, hashes, completeness and, optionally, chain inclusion. Carriers are OP_FALSE OP_RETURN outputs with ordfs/dir (a gib directory manifest) or ordfs/patch. A gib commit and a clone of it yield the same store.

Released apps and snapshots are deployed on chain as Bitcoin transactions, so a genesis or an install can point at an outpoint as well as a git commit.

Checkpoints

A packet whose scope is a skein-state record is a checkpoint. It restores onto an empty store without rebuilding the index, as long as it runs under the same identity. A checkpoint of a skein with the shell app is ~88 MB, because it includes the shell and Python.

Deploying files vs booting

Booting sets up a new store. Deploying sends files into a running instance: an agent’s SOUL.md, IDENTITY.md and skills/ go in as an ordinary signed message from the owner to the kernel’s objects operation.

Installing an app

An app is a tree with etc/app.json: its programs, its configuration, what it provides and requires, the dispatch rows it asks for, and optional start and stop messages. skein-host install <repo | dir> --instance <handle> checks it and reads the rows aloud. Once the owner approves, it sends four kinds of admin message: objects (the tree and program records), head (<app>/app → the app record), dispatch (one per row; web paths under /<app>/), then start. An app writes only heads under its name. Uninstall sends stop and removes its rows. A set of apps that go together installs the same way, one app at a time.

Upgrades

An app upgrades by being installed again. Its state is kept, and rows the new version no longer asks for are removed. A change to the kernel’s log format (format 8) means a new store: older formats are refused, not migrated.
