Technical

Architecture

A deterministic WASI machine over a content-addressed graph. It has three layers: one kernel, a catalogue of programs, and several runtimes that drive the kernel from outside.

The runtime judges nothing. Everything that matters is decided by programs inside the kernel and written to the store.

Kernel

The machine: store, log, scheduler, the WASI implementation and skein’s own imports, over wasmtime (C API, statically linked). One implementation, kernel-zig, which also compiles to wasm32-freestanding for the browser. CLI: skein-kernel serve | replay | shell | dump | fuel.

Programs and the SDK

A catalogue, not a fixed set: front door, messagebox, wallet, resolve, overlay, fetch, p2p, the workbench programs (run, objects, head, subscribe, loop) and the SDK they’re written against. Each genesis wires its own subset; none is mandatory. The stock programs are Zig, 70–670 KB each.

Runtimes

Whatever drives a kernel from outside. A runtime implements one contract: admitting entries, making calls, giving the kernel a store, and answering its outbound requests (signing, HTTP, libp2p). How it holds keys, where it stores bytes and how it’s deployed are its own business. Today there’s a server runtime and a browser runtime, and the same history replays under either.

The kernel’s whole surface

admit
The one call in that writes: append a log entry, then run the steps it drives.
call
Run a program function over current state. No entry, no writes, not replayed; its fuel goes to the host’s ledger. Every web read is one of these.
wallet
Out: key operations, answered by the runtime’s signer.
http
Out: a request, made by the runtime’s proxy and recorded with its response on the step. The proxy signing both is designed.
libp2p
Out: publish, dial, send, receive, close. Recorded like http.

Data model: git and Bitcoin in one graph

Every durable thing is a record: one IPLD object named by its CID. Git objects, Bitcoin structures and skein’s own records use different codecs and hashes, but they all live in one store and link to each other by CID.

Families of record

Family
Codec · hash · what the CID equals
skein
dag-cbor · sha2-256. Log entries, thread origins and updates, messages, index nodes, the state record.
git
git-raw · sha1. A tree’s CID is its git object id. A scanned directory hashes identically to git write-tree.
bitcoin
bitcoin-block (0xb0) · dbl-sha2-256: CID = block hash. bitcoin-tx (0xb1): CID = txid. Exactly 64 bytes under bitcoin-tx is a Merkle node, whose CID is its Merkle hash.
raw
Wasm modules and the Python stdlib.

Links run from the newer record to the older one by CID, whatever the codec. Only transaction inputs add “spends” edges to the index.

Git mapping

A repository in a tree is an ordinary git repository, except that .git/objects is synthetic: each loose object is served on the fly from its git-raw record, and writes are inflated, sha1-checked and kept as records. No object is stored twice, and there are no packs. An agent’s deployed tree is its repository’s tree.

Bitcoin mapping

Headers decode to {version, previousblockhash → link, merkleroot → link, time, bits, nonce}; transactions to {version, vin: [{txid → link, vout, …}], vout, locktime}, with bitcoind’s field names. Proofs are held sparsely: receiving a BUMP (BRC-74) checks its root against the header at that height, then stores each node it reveals. Conflicting nodes and wrong roots are refused. A proofs map records txid → {block, depth, position}, and a proof is rebuilt by walking down from the header by the position’s bits.

Chains

Anything that changes is a chain: an origin (its identity) and updates carrying origin, prev and seq. Point at the origin for “as it is now”, at an update for “exactly this version”. Threads, heads, subscriptions and the address book are all chains.

The index and the state record

The store is a key→bytes map plus one pointer. Each query the scheduler needs is its own Merkle search tree (fan-out ~32, canonical: the same pairs give the same root in any order): log, unique, chains, threads, resting, sleepers, awaits, edges, heads. One skein-state record holds the log tip and every map’s root. Its CID is the instance’s single mutable pointer and a function of the log: same log, same state CID.

Cost: 2.5–7.5 new index nodes (0.6–4.2 KiB) plus ~1 KiB of state records per log entry. Pruning old index history is designed, not built.

Edges

The edges map indexes who points at what, derived from records a step keeps: launched-by, depends-on, resolves, record refs, and spends for kept transactions’ inputs. “Who spent txid:vout” is a prefix scan. Rejection propagates along spends, admits and derives-from.

The kernel and VM

A WASI machine where every input is a log entry and every value that didn’t come from the log is recorded. Replay is exact, and computation is metered by instruction count.

ABIs

Programs are WASI preview1 core modules or WASI 0.2 components (world skein:kernel/handler). The kernel tells them apart by the binary preamble and gives both one behaviour: 0.2 filesystem and io calls are answered by the preview1 implementation. Imports the kernel doesn’t answer (sockets, say) link as traps.

Two kinds of syscall

Pure
Files, pipes, spawn, stdio, clock, random. Answered inside, deterministically, never recorded.
Recorded
wallet, http, libp2p. The request and answer are written on the step’s update; replay serves them from there, and a request that differs on replay is a divergence.
Graph
get/put/putblock by CID, keep, launch, await, advance (heads), subscribe, deadline, edges, call.

Time

The runtime stamps each entry at admission. Inside a step, t = max(last + 1, stamp + fuel), one unit of fuel per clock tick: time never repeats, never goes back, and is recomputed exactly on replay. A shell and its children share one meter and one clock. Busy-waits end on their own. Sleep is a deadline; the waker admits one wake entry when it comes, and there are no periodic wake-ups.

Randomness

SHA-256(key ‖ counter) blocks, key = SHA-256(entry CID ‖ thread CID). Python’s random, uuid4, QuickJS Math.random and git’s temp names all draw on it and replay identically. It’s predictable from public records, so secrets are made by the signer instead.

Fuel

wasmtime fuel is on for every step and summed across everything in it (handler, shell, children, nested calls). The limit is fuelPerStep (default 1012); running out ends the step errored, deterministically, and it’s never retried. Kernel calls have their own limit (1010) and are charged to the host ledger. skein-kernel fuel is the billing query. Overhead is 0–9%. In the browser, where V8 has no fuel, the kernel instruments each module to count its own, and the counts match wasmtime’s.

Replay

skein-kernel replay rebuilds a store from its log with no wallet or network. The equivalence suite replays 16 real histories twice, natively, instrumented and in headless Chrome, and requires identical dumps, fuel and explorer pages. Signatures are deterministic (RFC 6979), so they replay too. Crash recovery is replay at hydrate time: a cut-off step runs again.

Userland

  • Shell: brush (bash-compatible, Rust) over uutils coreutils, plus find, xargs, diff, jq (jaq), sed, awk, tree and grep. Pipelines run stage by stage, with 64 MiB pipes.
  • git 2.55 in C via wasi-sdk: init to merge (three-way, conflicts), tag, fsck. No remotes, no packs. Commit dates come from the in-step clock, so commit IDs replay.
  • qjs (QuickJS-ng) registered as node with a sync Node shim, and CPython 3.14 with its stdlib mounted read-only. No npm, no pip, no sockets.
  • Size: 13.7 MB for the shell toolset, plus 19.1 MB for the script runtimes.

Browser build

The same kernel for wasm32-freestanding (2.4 MB) in a Worker, with IndexedDB as the store. It needs cross-origin isolation. It runs preview1 modules only, with no libp2p yet. Logs cross between browser and native in both directions.

Messages and network

The instance is an HTTP server. BRC-103/104 is the network, BRC-33 is the mailbox, BRC-169 is discovery, and only messages are state.

The front door

Each instance has its own origin (<handle>.host, or /@handle). The runtime forwards every request as one kernel call of the front-door program, which runs the BRC-103/104 handshake and verifies each message inside the VM. The caller is the identity key the session proved; there are no accounts. Answers are signed on the session through the runtime’s signer.

etc/routes.json maps paths to program functions (auth defaults to BRC-104; "none" is for open routes like overlay submit). etc/reads.json gates read routes by caller. A handler answers {status, body, admit?, then?}, and admit lists the entries to write.

The persistence rule

Message arrives
One mail entry, carrying the signed BRC-104 request, so authorship verifies from the log with keys alone.
Read or poll
Nothing. Tested at 10,000 polls: 0 entries, 0 bytes.
Handshake
Nothing. Sessions are held in memory, never in the log; after a restart the client simply handshakes again.
Acknowledgement
One entry: the reader’s pointer moves.
Sending
Part of the sending step: a recorded http call and the record it put. Not an entry.

Routing inside

A body with replyTo resumes the thread awaiting that record, but only from the identity it was sent to. Otherwise a message is routed by subscription on (sender, box), first match wins. “A subscription is the permission”; the subscription table is itself a chain. No match means it’s recorded and nothing runs.

Mailboxes, delivery, discovery

  • Messagebox program: BRC-33 send/list/ack (JSON or BRC-231 CBOR). An instance’s own boxes keep no list: admission is the acknowledgement, and the log is the queue.
  • Mailbox instances: an outside identity (a person, the inference peer, a browser tab) gets an instance with only the front door and messagebox. There’s no separate messagebox host.
  • Delivery: send looks up the address book (head peers: key → mailbox URL), reuses a BRC-104 session, and POSTs as a recorded call. Transient and permanent failures are distinguished; an unknown key is “no route”.
  • Discovery (BRC-169) is a program, not core: manifest, then handle → identity key and messagebox, as recorded calls.

Inference protocol

The loop sends {model, thinking?, tools?, parent?, nodes}, where nodes are only the turn records new since the last request, each with its CID and parent. The inference peer stores nodes per sender, walks back to the root and sends the engine the whole chat. If it lacks a node it answers {missing: [cid]} and the loop resends once. The completion arrives as mail with replyTo, and resumes the thread.

libp2p

The runtime runs a libp2p node for each instance that asks for one (GossipSub with strict signing). Inbound arrives as front-door calls; an accepted topic message is one p2p entry that re-verifies from the log; duplicates and rejects write nothing. Outbound is the recorded libp2p import. The peer key is separate from the identity key and never holds funds.

Designed, not built: the front door forwarding admitted entries on every transport (today a transaction arriving by pubsub doesn’t persist overlay state the way POST /submit does).

Wallet and overlays

The wallet is split in two: the keys stay outside with the runtime’s signer, and wallet state lives inside as records. The overlay node shares the same chain and settlement core.

The signer

The kernel holds no keys. Key operations (get public key, sign, encrypt/decrypt, HMAC, verify) are requests to the runtime’s signer, which might be a hosting service’s key store, a hardware module, or the user’s own BRC-100 wallet in a browser tab. A signing request carries a key reference and a 32-byte hash, nothing else. How keys are made, stored and derived is the runtime’s business and outside the skein.

The wallet program

wallet-zig over bsvz, compiled to wasm. Operations include headers, internalize (BRC-100 internalizeAction on Atomic BEEF), proof, createAction, signAction and list. The builder picks the largest spendable outputs first, sends change to a fresh BRC-29 key, and returns Atomic BEEF with ancestry back to proven transactions. It matches go-sdk’s ProtoWallet byte for byte on shared test vectors. A genesis opts into it; it isn’t there by default.

SPV and headers

The anchor is the network’s genesis header, a constant. Every header must link, meet its proof-of-work target and carry the most work. Difficulty adjustment and timestamps aren’t checked, by decision. A payment validates synchronously or fails. A signing-only wallet needs no headers; the full chain (~72 MB) lives only in an instance fed by a header service. Chronicle rules are on by default.

Feeds

The runtime holds subscriptions an instance declares (a header stream, and transaction status callbacks) and admits each item as a plain event entry. It judges nothing: headers and proofs validate themselves inside, and a broadcast status is provisional until there’s a proof.

Settlement

Unproven, proven or rejected is computed, never stored. Rejection bubbles through spends edges; reorgs revert proofs. Settlement is state to read, not an event to push. Threads fork, they don’t replay: a rejection reaches a thread as a new input, and history stays.

Overlay node

An instance can serve BRC-22/24 through its own front door (POST /submit, POST /lookup, open auth). Submit decodes the BEEF once into records in the call’s scratch space, runs SPV, and asks topic managers identify(tx: cid, …). Nothing persists unless a topic admits; otherwise it answers 200 with an empty STEAK and the store is byte-identical. Lookup services keep their own maps and get admitted/spent/rejected hooks. Tested against the stock @bsv/sdk broadcaster and resolver.

Not built: SHIP/SLAP advertisement, GASP sync, certificates, header catch-up, proofs on demand. One broadcaster per host is designed.

Genesis and deployment

An instance’s first log entry, its genesis, names who it is and the tree it boots from. Everything after is a consequence of that entry and the ones that follow.

The system tree

bin/<name>.wasm | .cid | .json   programs
etc/config.json                   defaults, peers, feeds, owner, libp2p
etc/subscriptions.json            (sender, box) → program   (required)
etc/routes.json                   HTTP path → program fn
etc/reads.json                    who may call read routes
SOUL.md, IDENTITY.md, skills/…    the instance's own files

Booting pre-fills the store and writes a genesis naming the tree; processing it sets head main. The genesis also fixes the owner, the default limits and the owner’s mailbox for the life of the store.

Two sources, one loader

  • A directory, scanned into git objects, or a tree CID already in a store.
  • A chain packet: a BEEF bag plus a scope CID, verified offline for scope, hashes, completeness and, optionally, chain inclusion. Carriers are OP_FALSE OP_RETURN outputs with ordfs/dir (a gib directory manifest) or ordfs/patch. A gib commit and a clone of it yield the same store.

Checkpoints

A packet whose scope is a skein-state record is a checkpoint. It restores onto an empty store without rebuilding the index, as long as it runs under the same identity. A stock-system checkpoint is ~88 MB, because it includes the shell and Python.

Deploying files vs booting

Booting sets up a new store. Deploying sends files into a running instance: an agent’s SOUL.md, IDENTITY.md and skills/ go in through the objects box as an ordinary signed message from the owner.

Upgrades are re-genesis

New program versions apply to new geneses; an existing store keeps the modules its genesis names, and older formats aren’t migrated. Upgrading today means a new store.

Not built: a command that takes a commit ID directly, publishing packets on chain (the packet writer makes never-broadcast transactions for tests), and checkpoints anchored as gib heads.
