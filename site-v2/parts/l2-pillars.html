What it is · 1 of 3

The sandbox: a computer with no side doors

A skein runs programs the way any computer does. What’s different is what the programs don’t get: no disk, network, clock or randomness of their own. Everything a program can read comes from the skein’s history, so anything it does can be run again and checked.

What runs inside

Programs are ordinary WebAssembly compiled against the standard WASI interface, so they’re written for WASI, not for skein. Anything that compiles to plain WASI can run: Rust, C, Zig, Go. built

Each skein comes with a working userland:

  • a bash-compatible shell with coreutils, grep, sed, awk, find, diff and jq;
  • real git (2.55): commit, branch, merge, log, diff;
  • JavaScript (QuickJS, with a small Node shim) and Python 3.14;
  • the conversation loop that drives a language model, when there is one.

What’s missing, and what takes its place

A normal program has
A skein program gets instead
A disk
Files and folders from the graph. A working directory is a git tree, named by its hash.
The network
Nothing direct. To reach outside it sends a message or makes a request, and the request and its answer are written into the history.
A clock
The time the current input arrived, plus the work done since (1 unit of work = 1 clock tick). Time never runs backwards and replays exactly.
Randomness
A stream derived from the hash of the current input. It’s repeatable, so it’s never used for secrets. Secrets are made outside, where the keys are.
Other processes
Only what it launches itself, inside the same sandbox, on the same meter.

Every step is metered

The sandbox counts the instructions every step executes (its “fuel”) and writes the count into the history. There’s a limit per step. Billing is then just a question you ask of the history, and anyone who replays it gets the same numbers. built

Any step can be run again

A step’s inputs are all in the history: the message that woke it, the files it saw, the answers to anything it asked for. Run it again and you get the same bytes out. So you check what a program did by re-running it, not by trusting a log that someone wrote about it.

This is tested, not claimed: the test suite replays every stored history into a fresh store, twice, natively and in headless Chrome, and requires identical results. built

Where the sandbox runs

The kernel is written in Zig and runs on a server over wasmtime. The same kernel compiles to run in a browser tab, keeping its graph in the browser. A history written in the browser replays on the server, and the other way round. built

Honest limits today. No package managers (npm, pip), no threads, no streaming pipes (each pipeline stage runs to completion), and no tar or gzip yet. Programs that need a native binary or an outside service reach it by message, as a separate party.

What it is · 2 of 3

Keys and the door

A skein is an identity. It has its own key pair, its own Bitcoin wallet, and one way to deal with the world: through a door where everything that crosses is signed or proven.

An identity of its own

Every skein has an identity key. People, programs and other skeins address it by that public key, and it authenticates them the same way: by key, never by name or account. A handle like @martha is only a way of finding the key. built

Keys never enter the sandbox

Programs can ask for a signature, but they can never read a key. Signing is a request to a separate signer outside the sandbox, which sees a reference to a key and a 32-byte hash and nothing else. Each request and the signature that came back are written into the history, and signatures are deterministic, so replay matches exactly. built

Where the keys actually live is up to whoever runs the skein: a hosting service’s key store, a hardware device, or your own wallet in a browser tab. The skein only ever sees public keys and the signatures it asked for.

A wallet inside

The wallet (the BRC-100 interface) runs inside the sandbox as a program. Its coins, transactions, proofs and block headers are records in the graph like everything else. It builds and signs transactions (through the signer) and checks incoming payments against their proofs before it accepts them. built

The door: what crosses, and how it’s proven

Every skein is a small web server at its own address. Each request goes through one program, the front door, which runs mutual authentication (BRC-103/104) and decides what gets written.

What crosses
How you can check it later
A message
Signed by its sender. The signed request is kept with the message, so who sent it can be verified from the record alone, years later.
A payment
A transaction with its ancestry and Merkle proofs (BEEF), checked against block headers when it arrives.
Block headers and proofs
Prove themselves: each header must chain back to Bitcoin’s genesis with valid proof of work, and each proof must hash up to a header.
A peer-to-peer message
Signed by its publisher (libp2p), and re-verifiable from the record.
Something the skein asked for
A web request goes out through a proxy the host provides, which signs the request and the answer it got. Both are written on the step that made them, so the step replays. designed

Only state gets written

Reads, polls and handshakes leave no trace. A message that arrives is one record; checking your inbox ten thousand times writes nothing (that’s a test). A record is written only when the state actually changes. built

Why this matters

  • Every record has an author you can check.
  • Payments are proven, not claimed.
  • A skein can hold money and do things with it, and you can see exactly what it signed and why.

What it is · 3 of 3

The graph: history you can branch

Everything a skein holds is one graph of records, each named by the hash of its contents. Nothing is edited in place. A change is a new record that points at the one before it.

Named by content

A record’s name is a fingerprint of what’s in it. The same content always gets the same name and is stored once. Change one byte and it has a new name. Git works this way, and so does Bitcoin: a transaction’s ID is the hash of the transaction.

That’s why the graph can hold both. A folder’s name in the graph is its git tree ID, so a repository is already part of the graph. A transaction’s name is its txid, and a block header’s is its block hash. built

What’s in it

  • Files and folders, as git objects.
  • Messages that came through the door, with their signatures.
  • Steps programs took, with the work they cost and the answers to anything they asked for.
  • Bitcoin records: transactions, block headers and the Merkle proof nodes between them.
  • Links between them: which step started which, which transaction spends which output. You can ask “what spent this coin?” or “what did this message lead to?”.

One small record at the top points at all of it, so the whole state of a skein has a single hash. Two skeins that took in the same inputs have the same hash. built

Searchable by how things connect

Because every record links to what it came from, the graph can be searched by those links, not just by text. From a message you can find the conversation it belongs to, the steps it set off, the files those steps changed and the payments they made. From a coin you can find what spent it and why.

That changes what an agent working in a skein can see. It isn’t limited to its current chat log. It can see every conversation the skein has had, how each connects to the others, and the work and money that came out of them: the whole graph, not a transcript. Programs in the skein can follow these links today. built Handing the same view to a model as a tool is next. not yet

Records only ever point backwards. A head is a named pointer to one of them; branching is making another.

Heads, branches and merges

Things that change over time (a conversation, a running task, a project’s files) are chains: a first record and a series of updates, each pointing at the one before. A pointer to the first record means “as it is now”; a pointer to an update means “exactly this version”.

A head is a named pointer into the history, like a git branch. It moves only when something deliberately moves it. Because old records never change, any earlier point is still there to start from.

Where branching works today

Files

Named heads point at file trees, and real git runs inside: branch, three-way merge, conflicts. built

Conversations

Each turn names its parent turn, so a fork is simply a new turn that names an earlier parent. The records support it; there’s no button for it yet. records built

A whole skein

Its state is one hash, so a checkpoint can be packed up and restored on another host. built Starting a new skein from another’s earlier point, or merging two skeins, isn’t designed yet. not yet

Why this matters

  • Auditing is reading, not reconstructing: the history is the state.
  • Two states compare by one hash, and syncing means copying the records the other side is missing.
  • Trying something risky is cheap: branch, try it, keep what works.
