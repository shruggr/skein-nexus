What you can do

Watch a model work, turn by turn

When a skein talks to a language model, every request, every answer and every tool the model uses becomes a record in the graph. You can read back any turn, re-run what the tools did, and start again from any earlier point.

The model is outside the sandbox

Inference isn’t part of skein. A model provider is another party with its own identity, reached by message like anyone else. The conversation loop inside the skein sends a request; the answer comes back through the door as a signed message and wakes the loop up.

The model and how hard it thinks are chosen per request. Any OpenAI-compatible provider works behind the inference peer, and a skein with no model at all is just as useful.

The conversation loop is an app of its own, the chat app; a shell is another.

What gets kept, each turn

  • The prompt: the system prompt from the skein’s own files, and the user’s message.
  • The answer: the text, the model’s reasoning, the tool calls it made, which model answered, how long it took and the tokens it used.
  • Each tool call as its own step in the sandbox. A shell command runs there, and the folder it leaves behind is a tree with its own hash.
  • The signed reply from the inference provider, and the work each step cost.

Only new turns are sent to the provider. Each turn is a record with a hash, and the provider keeps the ones it has seen, so a long conversation doesn’t get re-sent in full every time.

Each turn names its parent. Following the parents back gives the whole conversation; naming an earlier parent starts a branch.

What that lets you do

  • Read back exactly what the model was shown and what it said, including its reasoning.
  • See the files the model saw and changed at every step, because each is a tree with a hash.
  • Re-run any tool step from the record and get the same result.
  • Look across conversations, not just this one. Every chat the skein has had is in the same graph, linked to the steps, files and messages it produced, so the model’s context can be the whole graph rather than one log.
  • Branch from any turn and try a different prompt or model, leaving the original intact.
What the record can’t do is make the model deterministic. Re-running a tool step reproduces it exactly; asking the model again may give a different answer. That’s why the model’s answer is kept as a signed message rather than recomputed.

What you can do

Give every agent, and every person, a skein

One skein per agent means each agent has its own keys, wallet, mailbox, files and history. People can have one too, even if all it does is hold their mail.

An agent’s skein

An agent is a skein with the chat app installed and a model behind it. Its personality and instructions are ordinary files in its tree (SOUL.md, IDENTITY.md, a skills/ folder), deployed into it by message. It has a handle, an address, a wallet and a mailbox. Anyone who knows its key can message it; whether it answers depends on its dispatch table, which says which senders may reach which program.

A person’s skein

A person’s skein needs no model. A mailbox skein has only the front door and a mailbox, and holds that person’s mail so other skeins always have somewhere to deliver. There’s no central mail server: every mailbox is its own skein. Registering one is a signed request from your wallet.

Finding each other

Messages go to keys. Handles (@martha) are how you find a key and its address, through the BRC-169 discovery lookup. Each skein keeps its own address book of keys it knows how to reach.

What you can do

Let skeins work with each other, in the open

Skeins message each other exactly the way you message them. There’s no separate channel for machines, so everything between them is signed and kept, on both sides.

One way of talking

One skein asks another something with the same kind of message a person would send. The reply comes back to the thread that asked, and only if it comes from the key the question went to. Each side keeps its own record of the exchange.

A person can ask one agent, which consults another over several back-and-forth hops, and the answer comes back to the person.

Broadcast, too

Skeins can also join peer-to-peer networks (libp2p). A message accepted from a topic is written as a record that re-verifies from its publisher’s signature. A rejected one is refused and kept in the history; a repeat is ignored.

Shared Bitcoin services

An overlay is an app: the overlay engine plus your own topic managers and lookup services, installed under one name. It takes transactions for its topics at /<handle>/<app>/submit, keeps the ones its rules admit, answers lookups, and shares what it admitted with peers over libp2p. If no topic admits a transaction, only the request is recorded. BSV-21 tokens and 1Sat Ordinals collections are the first overlays being written for it.

Paying each other

A skein’s wallet can receive a payment and make one, and a payment can ride on any message: to pay for work, or to pay for delivery to a mailbox.

Why the record matters here. Programs that message each other and hold money should be inspectable. Every message between them is signed, every step is kept, nothing can be deleted or rewritten, and any step can be re-run.

What you can do

One graph over all your work

Skein started with a plain problem. One project lives in several repositories on several machines, and every coding assistant keeps its own history and memory. None of it connects. A skein is one place where all of it can live together, whoever did the work.

Why it fits

  • Repositories are already part of the graph, because folders are stored as git trees. Importing a directory gives you its tree hash, and real git runs inside.
  • Every change arrives by a signed message or is made by a recorded step, so the history says who or what made it: you, a script, or an agent.
  • Named heads track where each line of work is, and nothing earlier is ever lost.
  • The same record serves a person reading back what happened and a program looking for context.

No model required

Many skeins won’t run a model at all. A skein that just keeps files, runs scheduled jobs, holds a wallet or indexes some data is a complete skein, and it still acts on its own. The model is one kind of driver among several.

Where this stands. The pieces exist: importing trees, git inside, heads, signed changes. The everyday workflow (keeping your working repositories and your assistants’ sessions flowing into your skein) is the direction, not a finished tool.

What you can do

Your own slice of Bitcoin, indexed and proven

Today, shared indexers and gateways answer questions about your coins and transactions for free. A skein keeps that information for you, in your own graph, with the proofs attached.

What it holds

Transactions under their txids, block headers under their block hashes, and only the Merkle proof nodes that connect your transactions to those headers. Proofs merge for free: two proofs from the same block share their nodes, because the nodes are named by their hashes.

Headers must chain back to Bitcoin’s genesis block with valid proof of work before they’re accepted. Payments are checked against them when they arrive. Consensus rules are current, including Chronicle.

One app per skein keeps this chain state, the chain app. The wallet and every overlay read it rather than keeping copies. You hand it a transaction with its ancestry and proofs (a BEEF): it records it, broadcasts it if it isn’t mined yet, and answers as the transaction is accepted and mined.

Settlement you can read

Every transaction is unproven, proven or rejected, and that status is worked out from the graph rather than stored as a flag. If a transaction is rejected, everything that spent from it is affected too, by following the “spends” links. A chain reorganisation reverts the proofs it invalidates.

Walk it

Each skein has an explorer that walks the graph: from a block header to its Merkle root, down the proof to a transaction, and on to whatever spends it.

Why keep your own

Your records don’t depend on a service staying up or staying honest. The proofs travel with the data.

Headers arrive from a feed. A transaction’s status and its proof come back from the Arcade the skein broadcast to. Headers and proofs check themselves against the chain; a status is Arcade’s word, and stays provisional until the proof arrives.

What you can do

Start from a commit, run anywhere

A skein boots from a tree of files: its programs, its configuration and its own documents. That tree can come from a folder, a git tree, or a repository published on chain. After that, the same skein can run on a server or in a browser tab.

The system tree

Programs live in bin/ as WebAssembly, and configuration lives in etc/: the dispatch table’s first rows (which sender may reach which program, by message box, web path or peer-to-peer topic) and which Bitcoin feeds to follow. Anything else in the tree is the skein’s own files. The skein’s first record (its genesis) names that tree by hash, so what it started from is fixed forever.

Apps on top

A genesis can be bare: the kernel’s tables and the owner’s admin rows, nothing else. Apps go in on top. Each app is its own repository, and the owner installs it into a running skein. The install shows the rows the app asks for and sends them only once the owner approves. A skein installs only what it uses: no web server, no peer-to-peer, no chain app if nothing needs them.

Where the tree comes from

  • A folder on disk, hashed into git objects. It gets the same hash as git write-tree.
  • A tree already in a store, by its hash.
  • A chain packet: Bitcoin transactions carrying a repository (via gib), plus their proofs, verified offline. A repository published on chain and a clone of it produce the same store.

Released apps and snapshots are deployed on chain as Bitcoin transactions, so a genesis or an install can point at an outpoint as well as a git commit. When the code comes from the chain, who published it and which version ran are both part of the record.

Same skein, different machines

The kernel runs natively on a server and also compiles for the browser. A history written in either replays in the other. A checkpoint (a skein’s state, packed with everything it references) can be restored on a second host under the same identity.

Running one

Where a skein runs

A skein runs on a host. The host can be a server running many skeins, your own machine, a browser tab, or an application with the kernel built in. The skein and its history are the same on each.

What every host does

It runs the kernel. It holds the keys and signs what the skein asks it to sign, outside the sandbox. It keeps the store. And it provides, or points to, the transports and services the skein’s tables name: HTTP, a mailbox, libp2p, a web proxy, a broadcaster, timers. A service may be the host’s or anyone’s; to the skein it is only an address in its book. The host decides nothing and routes nothing inside the skein: the skein’s own dispatch table does that. So a skein can move between hosts.

A multi-skein host

One process, one master secret, many skeins. Each skein’s identity key and its libp2p key are derived from that secret inside the process, so no secret is passed between tools. Each skein has its own address, its own store and its own libp2p node. This is what a service operator runs.

Every skein serves the same management page at its address: with your wallet connected, it creates a skein on the host, keeps the list of your skeins in your wallet, and installs apps into each.

The command line

One skein on your own machine, run by the same host code. It is for development and for personal use.

The browser

The kernel runs in a tab, in a Worker, with IndexedDB as the store and your wallet as the signer. Mail that arrives while the tab is closed waits in the skein’s mailbox, and timers fire when the tab is next open. Peer-to-peer runs over js-libp2p, with bootstrap nodes we provide.

Embedded in an application

The kernel linked into a standalone application, which supplies its own signer and transports.
