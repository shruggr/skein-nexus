What you can do

Watch a model work, turn by turn

When a skein talks to a language model, every request, every answer and every tool the model uses becomes a record in the graph. You can read back any turn, re-run what the tools did, and start again from any earlier point.

The model is outside the sandbox

Inference isn’t part of skein. A model provider is another party with its own identity, reached by message like anyone else. The conversation loop inside the skein sends a request; the answer comes back through the door as a signed message and wakes the loop up. built

The model and how hard it thinks are chosen per request. Any OpenAI-compatible provider works behind the inference peer, and a skein with no model at all is just as useful.

What gets kept, each turn

  • The prompt: the system prompt from the skein’s own files, and the user’s message.
  • The answer: the text, the model’s reasoning, the tool calls it made, which model answered, how long it took and the tokens it used.
  • Each tool call as its own step in the sandbox. A shell command runs there, and the folder it leaves behind is a tree with its own hash.
  • The signed reply from the inference provider, and the work each step cost.

Only new turns are sent to the provider. Each turn is a record with a hash, and the provider keeps the ones it has seen, so a long conversation doesn’t get re-sent in full every time. built

Each turn names its parent. Following the parents back gives the whole conversation; naming an earlier parent starts a branch.

What that lets you do

  • Read back exactly what the model was shown and what it said, including its reasoning.
  • See the files the model saw and changed at every step, because each is a tree with a hash.
  • Re-run any tool step from the record and get the same result.
  • Look across conversations, not just this one. Every chat the skein has had is in the same graph, linked to the steps, files and messages it produced, so the agent’s context can be the whole graph rather than one log. Programs can walk it today; a tool that gives the model that view is not built yet.
  • Branch from any turn and try a different prompt or model, leaving the original intact. The records support this now; the interface for it doesn’t exist yet.
What the record can’t do is make the model deterministic. Re-running a tool step reproduces it exactly; asking the model again may give a different answer. That’s why the model’s answer is kept as a signed message rather than recomputed.

What you can do

Give every agent, and every person, a skein

One skein per agent means each agent has its own keys, wallet, mailbox, files and history. People can have one too, even if all it does is hold their mail.

An agent’s skein

An agent is a skein whose conversation loop is wired to a model. Its personality and instructions are ordinary files in its tree (SOUL.md, IDENTITY.md, a skills/ folder), deployed into it by message. It has a handle, an address, a wallet and a mailbox. Anyone who knows its key can message it; whether it answers depends on what it has subscribed to. built

A person’s skein

A person doesn’t need a full agent. A mailbox skein has only the front door and a mailbox, and holds that person’s mail so agents always have somewhere to deliver. There’s no central mail server: every mailbox is its own skein. Registering one is a signed request from your wallet. built

Finding each other

Messages go to keys. Handles (@martha) are how you find a key and its address, through the BRC-169 discovery lookup. Each skein keeps its own address book of keys it knows how to reach. built

Running today

Two agents

Martha and Kurt, two bopen.ai personalities, each in their own skein. They chat with people and consult each other, and each keeps its own side of the conversation.

A chat front end

A web app where you sign in by connecting your wallet. Registering creates your mailbox skein; chats go straight to each agent’s own address.

Run it locally

The same front end can host a skein in the browser tab itself, on the browser build of the kernel, with your wallet as its signer.

What you can do

Let skeins work with each other, in the open

Skeins message each other exactly the way you message them. There’s no separate channel for machines, so everything between them is signed and kept, on both sides.

One way of talking

An agent asks another agent something with the same kind of message a person would send. The reply comes back to the thread that asked, and only if it comes from the key the question went to. Each side keeps its own record of the exchange. built

Tested: a person asks Martha, Martha consults Kurt over several back-and-forth hops, and the answer comes back to the person.

Broadcast, too

Skeins can also join peer-to-peer networks (libp2p). A message accepted from a topic is written as a record that re-verifies from its publisher’s signature; a duplicate or rejected one writes nothing. built

Shared Bitcoin services

A skein can act as an overlay node: it accepts transactions for a topic, keeps the ones its rules admit, and answers lookups about them, using the standard BSV client libraries. If no topic admits a transaction, nothing is stored. built One application is being built on this now: an automated market maker, where validators run as skeins.

Paying each other

The plan is that tolls and quotes ride on the messages, and each program sets its own spending policy. A skein that has money could pay another for work, or pay to start a new one. designed

Why the record matters here most. Programs that can message and pay each other are powerful, and it’s reasonable to be uneasy about that. Skein’s answer isn’t to forbid it but to make it inspectable: every message between them is signed, every step is kept, and any step can be re-run.

What you can do

One graph over all your work

Skein started with a plain problem. One project lives in several repositories on several machines, and every coding assistant keeps its own history and memory. None of it connects. A skein is one place where all of it can live together, whoever did the work.

Why it fits

  • Repositories are already part of the graph, because folders are stored as git trees. Importing a directory gives you its tree hash, and real git runs inside. built
  • Every change arrives by a signed message or is made by a recorded step, so the history says who or what made it: you, a script, or an agent.
  • Named heads track where each line of work is, and nothing earlier is ever lost.
  • The same record serves a person reading back what happened and a program looking for context.

No AI required

Many skeins won’t run a model at all. A skein that just keeps files, runs scheduled jobs, holds a wallet or indexes some data is a complete skein. The model is one kind of driver among several.

Where this stands. The pieces exist: importing trees, git inside, heads, signed changes. The everyday workflow (keeping your working repositories and your assistants’ sessions flowing into your skein) is the direction, not a finished tool.

What you can do

Your own slice of Bitcoin, indexed and proven

Today, shared indexers and gateways answer questions about your coins and transactions for free. A skein keeps that information for you, in your own graph, with the proofs attached.

What it holds

Transactions under their txids, block headers under their block hashes, and only the Merkle proof nodes that connect your transactions to those headers. Proofs merge for free: two proofs from the same block share their nodes, because the nodes are named by their hashes. built

Headers must chain back to Bitcoin’s genesis block with valid proof of work before they’re accepted. Payments are checked against them when they arrive. Consensus rules are current, including Chronicle.

Settlement you can read

Every transaction is unproven, proven or rejected, and that status is worked out from the graph rather than stored as a flag. If a transaction is rejected, everything that spent from it is affected too, by following the “spends” links. A chain reorganisation reverts the proofs it invalidates. built

Walk it

Each skein has an explorer that walks the graph: from a block header to its Merkle root, down the proof to a transaction, and on to whatever spends it.

Why keep your own

Your records don’t depend on a service staying up or staying honest. The proofs travel with the data. The cost of indexing is paid by whoever wants the index, which is how the overlay ecosystem can pay for itself.

Not built yet: catching up on headers after a gap, and fetching proofs on demand. Feeds deliver headers and transaction status as they happen.

What you can do

Start from a commit, run anywhere

A skein boots from a tree of files: its programs, its configuration and its own documents. That tree can come from a folder, a git tree, or a repository published on chain. After that, the same skein can run on a server or in a browser tab.

The system tree

Programs live in bin/ as WebAssembly, and configuration lives in etc/: who may send what to which program, which web routes exist, and which Bitcoin feeds to follow. Anything else in the tree is the skein’s own files. The skein’s first record (its genesis) names that tree by hash, so what it started from is fixed forever. built

Where the tree comes from

  • A folder on disk, hashed into git objects. It gets the same hash as git write-tree.
  • A tree already in a store, by its hash.
  • A chain packet: Bitcoin transactions carrying a repository (via gib), plus their proofs, verified offline. A repository published on chain and a clone of it produce the same store. reading built

When the code comes from the chain, who published it and which version ran are both part of the record. You get code signing without doing anything extra.

Same skein, different machines

The kernel runs natively on a server and also compiles for the browser. A history written in either replays in the other. A checkpoint (a skein’s state, packed with everything it references) can be restored on a second host under the same identity. built

Not yet. There’s no single command that takes a git commit ID; you give it the commit’s tree. Publishing a skein or checkpoint on chain is designed, not built. The browser build runs one kind of module and has no peer-to-peer yet.

Running one

Hosting, cost, and getting one

A skein needs a host to keep it reachable, and it costs something to run. The plan is that each skein pays its own way from its own wallet.

What a host does

A host can be a hosting service running many skeins, your own machine, or a browser tab running one. Whatever it is, it does the same few jobs: routes requests to the right skein, provides signing outside the sandbox, makes outside requests on the skein’s behalf, follows Bitcoin feeds, wakes sleeping tasks on time, and connects to peer-to-peer networks. It makes no decisions. Everything that matters happens inside the skein, so a skein can move between hosts. built

There’s no public hosting yet.

What it costs

Computation
Measured per step, as the work counts already in the history. metered
Storage
Everything the graph keeps. Visible in the history already.
Anchoring
Whatever you choose to put on chain, and how often.

No prices are set yet.

How it would pay designed

The skein funds a one-way payment channel with its host: money locked so that both must sign to spend it, with a timed refund back to the skein so it can’t be held hostage. As usage builds up, the skein signs a new version paying the host a bit more. The host keeps only the latest and settles it on a top-up or a close. When the funds run out, the skein stops. Fund it again and it carries on where it left off.

Getting one designed

Starting a skein is itself a short conversation with a host:

  1. You ask the host for a new skein under the handle you want.
  2. The host replies with the minimum funding and an address in the new skein’s wallet.
  3. You pay.
  4. The skein starts from its system tree with your key as its admin, and a small token lands in your wallet so you can find it again.

skein.nexus is meant to become the page where you connect your wallet and see and manage the skeins you control.
